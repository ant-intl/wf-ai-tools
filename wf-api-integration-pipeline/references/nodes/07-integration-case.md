# 节点 7 · 集成用例规划

> 对应 Harness 节点 `integration_case`（skill：wf-integration-case）。

**目标**：拉取开发者中心为应用生成的必过验收用例，与服务端严格 1:1，只做两件事——按业务相关性排定用例执行顺序、把每个步骤的服务端描述翻译成通过条件。
**完成标志**：客户确认方案，方案文件已保存。

## 铁律

1. **用例唯一来源是服务端**：必须先执行 `acceptance cases`。不得凭代码、接口文档、模板或会话历史臆造用例。
2. **严格 1:1**：服务端返回 N 个用例，方案里就是同样的 N 个，`caseOrderId` 一一对应；不得新造、合并、拆分或丢弃任何用例（包括看起来无关或重复的）。每个用例的步骤覆盖该用例服务端返回的**全部**步骤，`nodeDefineId` 一一对应，不得增删。
3. **步骤顺序不可改**：用例内步骤恒为服务端 `step` 升序；只能排**用例之间**的执行顺序。
4. **通过条件只能翻译**：`expect` 只能由该步骤的 `description`、`checkPoints`、`expectedResults` 翻译而来，不得放宽，不得追加服务端没写的条件。
5. **不用内部结果码**：`expect` 中不得出现 `IPAY_RS_*` 等内部 resultCodeId，一律使用用户可见语义（如 `resultStatus=S`、返回了 `payoutId`、状态为 `PROCESSING`）；也不得复用会话历史里的旧断言文本。

## 第 1 步：拉取必过用例

```bash
worldfirst acceptance cases --client-id <ClientId> --json
```

返回 `data`：`caseCount` 与 `cases[]`，每个用例含 `caseOrderId`、`caseDefineId`、`groupName`、`name`、`description`、`status`、`flowOrderId`、`interfaceUrl`，以及 `steps[]`（`nodeDefineId`、`step`、`name`、`nodeType`、`description`、`checkPoints`、`expectedResults`、`interfaceUrl`、`requestMethod`、`status`）。`cases` 已是必过用例全集，`steps` 已只含需要客户操作的步骤，**不要再筛选**。

- 命令失败（未登录、应用未授权、网络错误）：说明原因后停止（未登录 → 先完成 CLI 授权；应用未授权 → `worldfirst login --reauth` 勾选该应用），绝不改用其它来源凑用例。
- `caseCount=0`：告知「开发者中心尚未为该应用生成必过验收用例，请先在开发者中心完成接口选型与用例初始化后再继续」，停止。

## 第 2 步：按业务相关性排序

依据是业务数据流：上游用例产出的资源、单据、报价，是下游用例的输入或核对对象。典型主线（只保留服务端实际返回的用例，缺失的环节直接跳过，不得补造）：

| 场景主线 | 用例执行顺序 |
|---|---|
| 付款 / 转账 | 查余额 → 收款人准备 → 锁价 / 报价 → 付款预咨询 → 创建付款 → 查询付款状态 → 流水复查 → 账单核对 |
| 即期兑换 | 汇率查询 → 报价 → 兑换交割 → 交割查询 → 余额复查 |
| 远期外汇 | 报价 → 创建远期 → 远期查询 →（取消远期）→ 交割 |
| 持卡人与卡 | 创建持卡人 → 开卡 → 卡查询 → 卡交易账单 |
| 全球收款账户 | 开户 → 账户查询 →（更新 / 关闭） |
| 收款 / 来账 | 来账查询 → 来账列表 |

- `execOrder` 从 1 开始连续编号，覆盖全部用例，不重复。
- 有依赖的按依赖先后排；无依赖的排在主线之后，按 `groupName` 聚拢，方便客户按模块连续操作。
- 已 `status=FINISH` 的用例也保留（1:1），可排在最后。
- `scenario` 填业务场景名（如「单笔付款主链路」「账单与流水核对」），同一场景的用例尽量相邻。

## 第 3 步：逐步骤翻译通过条件

素材是该步骤的 `description` + `checkPoints[]` + `expectedResults[].description`（`successTip` 可作补充）。写法：一到两句中文，说清「做什么」+「看到什么算通过」。例如描述为「创建付款单并校验返回」→「调用创建付款接口成功，响应 `resultStatus=S` 且返回 `payoutId`，单据状态为 `PROCESSING` 或 `SUCCESS`」。

- 服务端描述中给出的状态、字段取值原样保留，不改得更严或更松。
- 描述含糊时只翻译写了的部分，可在末尾注明「以接口文档响应说明为准」；描述为空时写「按接口文档响应说明判定调用成功（服务端未提供更细的校验点）」。

## 第 4 步：自检（逐条核对后再展示）

- 方案用例数 = `caseCount`；每个 `caseOrderId` 都来自 CLI 返回，无重复、无遗漏、无新造。
- 每个用例的步骤数 = 服务端 `steps` 数，`nodeDefineId` 集合完全一致。
- `execOrder` 是 1..N 的连续整数。
- 每条 `expect` 非空，且不含内部结果码。

## 第 5 步：展示方案并确认

先用一两句话说明编排思路（共多少个必过用例、排出怎样的业务主线、哪些用例相互独立），再按场景分组用表格展示：执行顺序、场景、用例名、步骤（步骤名 + 通过条件）。方案只读，最后询问客户：确认方案，还是调整。

允许的调整**只有两类**：

- 调整执行顺序（如「先查账单再转账」）→ 重排 `execOrder`，重新展示完整方案；
- 调整场景归类或译文措辞 → 更新 `scenario` / `expect`，重新展示完整方案。

不允许、必须拒绝并说明原因的调整：增删、合并、拆分用例（「用例集由开发者中心生成，必须全部验收通过，可以调整执行顺序」）；增删步骤（「步骤由服务端用例定义决定」）；把通过条件放宽或收紧到服务端描述之外（「通过条件必须来自开发者中心的步骤描述」）。每次调整后所有 `caseOrderId`、`nodeDefineId` 保持不变。

## 第 6 步：保存方案

客户确认后，再执行一次 `acceptance cases` 做第 4 步的 1:1 核对（服务端用例集可能已变化，不一致则按最新结果重新规划），通过后写入方案文件，并更新进度文件（`acceptance.planFile`、`acceptance.confirmedAt`、本节点 `DONE`）。

### 方案文件

路径 `<工作区根>/.worldfirst/acceptance-plan.json`。只存 AI 的增值部分（顺序、场景、通过条件）；用例名、描述、接口路径等定义字段执行时以服务端最新返回为准，不在这里转写：

```json
{
  "clientId": "SANDBOX_XXXXXXXX",
  "confirmedAt": "2026-11-19T11:00:00+08:00",
  "caseCount": 2,
  "cases": [
    {
      "caseOrderId": "<服务端 caseOrderId 原样>",
      "execOrder": 1,
      "scenario": "单笔付款主链路",
      "name": "<服务端用例名，仅供阅读>",
      "steps": [
        { "nodeDefineId": "<服务端 nodeDefineId 原样>", "name": "<步骤名>", "expect": "<由服务端描述翻译的通过条件>" }
      ]
    }
  ]
}
```

保存后输出摘要：共确认 N 个必过验收用例（与开发者中心一致），按表格列出执行顺序、场景、用例、步骤数；询问是否进入执行集成用例。

## 边界

- 客户要求删除或合并用例：按上面的话术拒绝，并主动提供「调整执行顺序」作为替代。
- 客户提出服务端用例之外的业务规则问题：说明「该细节以 WorldFirst 官方文档为准」，不编造，也不据此修改用例集。
